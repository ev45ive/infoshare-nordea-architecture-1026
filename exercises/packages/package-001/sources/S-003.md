# Payment processing: provider contract notes

**Provider operations | Inquiry response | WD01, Europe/Warsaw**

The following is the current contract summary for the retailer’s launch inquiry. Sandbox and production use separate credentials. Sandbox requests do not move real money. Production credentials require business approval; that approval is outside this response.

## Request outcomes

A request can be **accepted**, **rejected**, or **pending**. “Accepted” means accepted for processing; it does not mean funds have settled. If the caller times out, the result is unknown to the caller. A lost response is not evidence of rejection or settlement.

The caller supplies a merchant reference. A status query for that reference returns the provider request currently associated with it. Sending the same reference again with the same immutable amount returns the existing provider request. Reusing the reference with a different amount is rejected as a conflict. A different reference can create a new provider request. The provider retains the reference mapping for 30 scenario days.

## Status and settlement

After response loss, query the reference to learn the current provider contract status. A retry does not itself establish settlement. Callbacks can be duplicated or arrive out of order. The status query is authoritative for the current provider contract status, but it does not provide a final settlement guarantee.

A settlement file is sent on the next business day. This contract does not promise instantaneous reconciliation.

## Integration boundary

The documented semantics do not establish that the retailer’s availability or consisency solutions. Evidence of those implementation details has not been provided in this inquiry.
