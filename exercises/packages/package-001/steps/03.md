# 1.3 Propose the API

## Use and do

Map the actions in your journey to example requests, responses, and resulting state. Use [S-003](../sources/S-003.md) when examining provider behavior; distinguish provider acceptance for processing from settlement. Draw one completed exchange and one timeout, rejection, or incomplete exchange. For each response, state what it proves, what remains unknown, and what the customer would see under your proposal. Include the merchant reference and immutable amount where relevant, and explain how a repeated request would be recognized. Avoid claiming your design persists or reconciles anything unless your own record supports it.

## Record

Deliver a compact request/response trace and a brief note on ownership of each state transition.

## Challenge

If the same user action arrives twice or its response is lost, show how your proposed API distinguishes a safe status lookup from creating another provider request.
